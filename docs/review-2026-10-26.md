## The fixes, in order

Severities are the review's (High / Medium / Low). Each item: the problem, the fix,
and why it was done that way.

### High

**1. Impersonation is opt-in** (`a0f7152`, `deploy/compose.yaml`, `.env.example`)
- Problem: `AUTH_APP_ENABLE_IMPERSONATION=true` on every server. With it an admin's
  app token can mint tokens for any user, i.e. read every user's files; `users.sh`
  never used it.
- Fix: `${AUTH_APP_ENABLE_IMPERSONATION:-false}`; `.env` can turn it on. The user
  chose opt-in (rather than removing it) because the management tool outside this
  repo may need it. `test/check-permissions` still needs it in the test env.

**2. `users.sh` keeps no admin token on disk** (`a289e84`), **and revokes it**
(`11fba9c`)
- Problem: `.admin-token` held an admin app token valid for a year, never revoked.
- Fix: one token per run (`--expiration 10m`), held in a shell variable, created
  once in the command dispatch (not inside `api()`, which runs in subshells, so it
  would make a token per call). An old `.admin-token` is deleted with a note that
  its token stays valid until revoked in the web UI. At exit (also after `die`) the
  token is revoked: `DELETE /auth-app/tokens?token=<token>`. Upstream's auth-app
  accepts the plain token (reva `jsoncs3.InvalidateAppPassword` compares it with
  the stored argon2 hash). Tokens may be diceware words with spaces, so the value is
  URL-encoded with yq's `@uri`. `lib.sh` has `EXIT_HOOKS` for this.
- `api()` now passes the URL to curl in its config on stdin too, so the token is
  never on a command line.

**Found in the test env (2026-10-26, after this branch was pushed): reva has two
copies of decomposedfs.** `pkg/storage/pkg/decomposedfs` is used by the `posix`
driver (OpenCloud 7.2's default, and the test env's), `pkg/storage/utils/decomposedfs`
by `ocis` and `s3ng`. `reva/0002` and `reva/0003` first patched only the `utils` copy,
so on `:test-6cf5a89` neither did anything (PUT/TUS/COPY over a file with content were
accepted; the storage log's source lines name `pkg/storage/pkg/decomposedfs`). Both
patches now change both copies, the same-content exception included, with the tests
in both (the `pkg` copy's test env answers `AssemblePermissions` with the owner's
permissions for good, so its tests clear that answer first). Each refusal test fails
without its change; the full `decomposedfs` suites (both copies), `conversions` and
`fs/posix/...` pass. The `pkg` copy also checks a declared checksum before it creates
the new file (`FinishUploadDecomposed`), so the same-content exception holds there.

**3. "Can't delete" can't replace a file with content** (`65c7956`,
`patches/reva/0003`) and **no "Replace" in the web's upload dialog** (`5b83513`,
`patches/web/0013`)
- Problem: on a "Can't delete" share the server accepted an upload over an existing
  file (decomposedfs `InitiateUpload` checks only `InitiateFileUpload` on the file),
  so any WebDAV client could replace content, even with an empty file. The role's
  description says "No editing or deleting".
- How it was found to be narrow: PUT, TUS and COPY of a file onto an existing one
  all end in `InitiateUpload`. MOVE/rename onto an existing name, and COPY of a folder onto one,
  already delete the target first and need `Delete`.
- Fix (reva): one `if` in `upload.go` after upstream's permission check, the logic
  in a new `upload_custom.go`: refuse when the file exists, has content
  (`Blobsize > 0`) and the permissions are "Can't delete"'s set: upload and move,
  `GetQuota`, no `Delete`, no `RestoreRecycleItem` (reva writes `W` only with
  `InitiateFileUpload` + `RestoreRecycleItem`). The same set `reva/0001` reports
  `NV` for. Upstream's roles keep overwriting (the user's rule: upstream's roles
  behave as upstream's).
- **Empty-file exception** (the user agreed): Windows Explorer ("Map network drive")
  and macOS Finder create a file empty, then upload its content over it; without
  the exception they'd leave empty files. Replacing an empty file loses nothing.
- **Same-content exception** (`f12e9a1`, the user agreed): a client whose upload
  went through but whose answer got lost retries, and the retry was refused (the
  file is there, the client shows an error). An upload is now accepted when the
  client declares a checksum (`OC-Checksum` on PUT, TUS `checksum` metadata; ocdav
  passes both to `InitiateUpload` as `"sha1 <hex>"`) equal to the file's stored one
  (`ocis.cs.<algorithm>` attributes). Safe because `FinishUploadDecomposed` checks
  the content against the declared checksum before replacing anything (the posix
  driver uses the same sessions). Only SHA-1 and MD5: content with a given Adler-32
  is easy to make. The desktop apps send SHA-1. **The web sends no checksum**
  (`TUS_ALLOWED_META_FIELDS` in `web-pkg/src/services/uppy/uppyService.ts` is
  `name` and `mtime`; tus-js-client 4.3.1 and the XHR fallback have no checksum
  support), so a web upload that has to start over after its content arrived is
  still refused. Not affected: a resumed TUS upload (its session exists, it doesn't
  pass `InitiateUpload` again), and a retried creation request (for a new file
  `InitiateUpload` creates only a session, not the file).
- Known limits (told to the user): a user can rename a file and upload a new one
  under the old name (the original survives and can't be deleted by them); a
  client can't replace their own mistaken upload either; an office editor
  (Collabora/OnlyOffice, not in `deploy/`) would open such files in edit mode
  (it decides from the upload permission) and fail to save.
- Fix (web): `ResourceConflictModal` gets a `hideSecondary` prop; the upload
  conflict code (`web-app-files/.../actions/upload.ts`) marks a file conflict
  `replaceable: false` when the existing file reports `NV` without `W` (only
  "Can't delete" has that) and has content, hides "Replace" for it, and doesn't
  apply a "Replace for all" to it (it gets its own question). The conflict shape
  stays `{ name, type }` otherwise, because upstream's spec compares it exactly.
- Tests: `upload_custom_test.go` (refused with content; accepted for a new file,
  an empty one and the same content by SHA-1 or MD5; refused for other content and
  for Adler-32; unchanged for Can upload/Can edit) and two `*.custom.spec.ts`
  files; the new-behaviour cases fail without the change.
- **Known gaps** (reviewed by the user on 2026-10-26):
  - *Other web paths*: `web/0013` hides "Replace" only in the upload dialog.
    Uploading a folder that merges into one with the same name, and paste or drag
    with "Replace", still try to replace files; the server refuses each file with
    an error, nothing is lost. Acceptable for now; a later web patch could skip or
    ask for such files (optional).
  - *macOS Finder* writes AppleDouble files (`._name`) next to files, sometimes
    twice, and rewrites `.DS_Store` in folders it opens; a second write with
    content is a replace and is refused. Only a real Mac shows whether Finder
    reports errors (test plan, step 4). If it does, the fix is a narrow exception
    in `reva/0003` for `._*` and `.DS_Store` (Finder's metadata, not user content;
    the cost: such names could be used to hide content others can overwrite). Not
    added on a guess.
  - *Retries without a checksum* (the web, see above) still show an error although
    the file arrived.

### Medium

**4. `X-Forwarded-For` for Authelia** (`64bf675`, SWAG template) — *downgraded to
Low after checking*
- Authelia takes the client IP from the first `X-Forwarded-For` entry
  (`internal/middlewares/wrap.go`), SWAG's `proxy.conf` appends to the client's
  header, so the client chose the IP in Authelia's logs and sign-in history. The
  review first said this bypassed brute-force protection; it doesn't: Authelia's
  regulation counts per username by default (`modes: [user]`).
- Fix: `proxy_set_header X-Forwarded-For $remote_addr;` in the `/authelia` location
  **before** the `include proxy.conf`. nginx then sends both header lines in that
  order (checked with a local nginx and SWAG's real `proxy.conf`), and fasthttp's
  header lookup returns the first (`peekArgBytes`). Caveat: if SWAG itself sits
  behind another proxy, Authelia sees that proxy's address.

**5. `users.sh add` leaves no account with the wrong role** (`8d5e818`)
- Problem: the account was created (OpenCloud makes it a User), then the role was
  set in a second call; a failure there left a client as a User (personal space,
  sharing, links), and without Authelia it could sign in as one in between.
- Fix: create it with `accountEnabled: false`, take the id from the POST's answer,
  set the role by id (`set_role_id`), then enable it; on any failure delete the
  account again. The steps run in subshells so a `die` returns. `set_role_id`
  refuses an empty application id (OpenCloud accepts an assignment with empty ids
  and leaves the user without a role).

**6. An unknown `SMTP_ENCRYPTION` no longer means plain text** (`29d8542`)
- Problem: Authelia's entrypoint treated anything but `ssltls`/`starttls` (typo,
  `STARTTLS`, empty) as plain SMTP with TLS off, sending the password in clear.
- Fix: explicit `none`; anything else stops Authelia with a message; `setup.sh`
  checks the value when `SMTP_HOST` is set.

**7. Changes to Authelia's user file aren't lost** (`9b16dab`)
- Problem: read file → yq in a container (~1 s) → `mv`; a concurrent `users.sh`, or
  Authelia rewriting the file on a user's password change, was overwritten (the
  password reverted).
- Fix: `update_users EXPRESSION` in `lib.sh` replaces all five read-modify-write
  pipelines: an `flock` on `authelia/.users.lock` (outside the watched `users/`
  folder; only a warning where `flock` is missing), a checksum (`cksum`) taken at
  read and compared before the `mv` (redo up to 3 times), the temp file under
  `umask 077` and removed at exit. The stand-in showed the old code losing one of
  two concurrent changes and the new code keeping both.

**8. The admin password doesn't stay in the container** (`78eb508`)
- Problem: `OC_ADMIN_PASSWORD` was in OpenCloud's environment for good (`docker
  inspect`), on `init`'s command line, and required in `.env` forever.
- Fix: on a new server (no `config/opencloud.yaml`) `setup.sh` writes
  `config/.admin-password` (600); the entrypoint runs
  `IDM_ADMIN_PASSWORD="$(cat …)" opencloud init` and deletes the file, or stops with
  "run ./setup.sh first" when there's neither config nor file. Upstream's `init`
  reads `ADMIN_PASSWORD`/`IDM_ADMIN_PASSWORD` (viper `BindEnv` in
  `opencloud/pkg/command/init.go`) — **to be confirmed by the test plan**.
  `setup.sh` asks for the password only while it's needed and reminds to empty it
  in `.env` (the user chose a reminder, not automatic blanking).

**9. A minimum password length, 3 for now** (`38da455`)
- Authelia `password_policy.standard.min_length: 3` (values below 1 aren't allowed;
  0 means its default 8), and `PASSWORD_MIN_LENGTH=3` in `lib.sh` for `users.sh` and
  `setup.sh`. The user chose 3 deliberately for the start; raise both together.

**10. A local build stops on stray changes in `upstream/`** (`b806e11`)
- `scripts/check-upstream`, run by `build-native` after `apply`: every patch must be
  applied in its current form (`git apply --reverse --check`), every changed
  tracked file must belong to a patch (plus the vendored reva files and the web's
  `package.json`, which `build-native` changes itself); untracked files only warn;
  `OC_CUSTOM_ALLOW_DIRTY=1` turns stray changes into a warning.

**11. Demoting a user disables their personal space** (`d61a8b5`,
`patches/reva/0002`; `fef80bb`, `users.sh role`)
- Problem: `users.sh role X client|employee|light` only changed the role; the
  personal space, and shares and public links from it, kept working.
- Found on the way: in reva's `UpdateStorageSpace` the restore check applies only
  to non-managers, and the owner manages their personal space, so a user could
  re-enable a space an admin disabled (`PATCH /graph/v1.0/drives/{id}` with
  `Restore: T`). The unit test confirmed it.
- Fix (reva/0002): restoring a personal space needs `Drives.DeletePersonal`, the
  permission disabling one needs (upstream's Admin has it); project spaces
  unchanged.
- Fix (`users.sh`): `role` to client/employee/light disables the space
  (`DELETE /graph/v1.0/drives/{id}`; asks on a terminal); back to user/admin
  restores it. Files are kept. The drive is found in the admin's
  `GET /graph/v1.0/drives?$filter=driveType eq 'personal'` (disabled ones show
  `root.deleted.state: trashed`); ids contain `$`, sent as `%24` (Graph
  unescapes). `api()` takes an optional header.
- Found in the test environment: the demoted user's own `/me/drives` still lists
  the disabled space, so the web showed Personal in the menu and opened it at
  sign-in with "Resource not found".
- Fix (web/0011, 0006, 0003): a new entry in the type table, `noPersonal`
  (Client, Employee): no Personal entry (also before the spaces are loaded), and
  the drive redirect ignores a personal space, so such a user lands on "Shared
  with me" like any Client. Hidden in the web for those types rather than
  dropping trashed personal spaces for everyone, so upstream's types keep
  upstream's behaviour; a new Client or Employee never has a personal space
  anyway. Check: demote alice (`users.sh role alice client`), sign in as alice:
  menu Shares + Deleted, start page "Shared with me"; `role alice user` brings
  Personal back.

### A. Non-destructive, on stack a (Authelia)

1. **An old `.admin-token` is cleaned up** (`a289e84`).
   ```sh
   echo old-token > .admin-token && ./users.sh list > /dev/null; ls .admin-token
   ```
   stderr: `Removed .admin-token (an older users.sh's token)…delete it under
   admin's Settings -> App Tokens.`; `ls` says the file is gone.
2. **A display name with a tab keeps `list`'s columns** (`ffa93b8`).
   ```sh
   ./users.sh add tabby --name "$(printf 'Tab\tby')" --random < /dev/null
   ./users.sh list | grep '^tabby '
   ./users.sh delete tabby < /dev/null
   ```
   One row: `tabby`, `Tab by` (a space where the tab was), then `-`, `user`,
   `yes`, `ok`, each under its heading. Before the fix the name's tab shifted
   every column after it.
3. **An option without its value** (`ffa93b8`).
   ```sh
   ./users.sh add zed --name; echo "exit $?"; ./users.sh list | grep -c '^zed '
   ```
   `--name needs a value`, `exit 1`, `0` (nothing created). The same for
   `--email` and `--role` as the last argument.
4. **`passwd` with an unknown argument** (`ffa93b8`).
   ```sh
   sum=$(cksum < authelia/users/users_database.yml)
   echo Pw-new-1 | ./users.sh passwd alice foo; echo "exit $?"
   [ "$(cksum < authelia/users/users_database.yml)" = "$sum" ] && echo unchanged
   ```
   `passwd USER [--random]`, `exit 1`, `unchanged`.
5. **A user that doesn't exist stops the command** (`8b5ac30`).
   ```sh
   ./users.sh email nobody x@deploy.test; echo "exit $?"
   ./users.sh disable nobody; echo "exit $?"
   ./users.sh delete nobody < /dev/null; echo "exit $?"
   ```
   Each: `OpenCloud: GET /graph/v1.0/users/nobody: HTTP 404 …` and `exit 1`, with
   no second line. Before the fix the commands went on with
   `/graph/v1.0/users/null` and printed a second error, or "e-mail is now…".
6. **The demotion prompt** (`fef80bb`), on a terminal (not piped):
   ```sh
   ./users.sh role alice client      # answer n
   ./users.sh list | grep '^alice '
   ```
   The question names the personal space, shares and links; `n` gives
   `Nothing changed`, exit 1, and `list` still shows `user`. Then run it again
   and answer `y`: `is now client` and `disabled alice's personal space`; then

7. **The token is revoked when a command fails** (`11fba9c`).

### B. Breaking the stack on purpose (stack a, then restore)

8. **OpenCloud stopped** (`12382b6`; the expectation the first version of this
   plan gave was wrong).
   ```sh
   docker compose stop opencloud && time ./users.sh list; echo "exit $?"
   docker compose start opencloud
   ```
   After about 25 s (5 tries, 5 s apart): `Couldn't create an app token for admin:
   service "opencloud" is not running`, exit 1. That's the token step, which now
   runs before the command, so a stopped container never reaches the "no answer"
   message. That message is for a container that's running while OpenCloud
   doesn't answer. It's hard to time: running `./users.sh list` within a second or
   two of `docker compose restart opencloud` may show it, or the token error;
   either is fine. It was checked with the stand-in `docker`.
9. **A bad `SMTP_ENCRYPTION` stops Authelia** (`29d8542`; `run.sh` checks only
   `setup.sh`'s refusal).
   ```sh

   sed -i 's/^SMTP_ENCRYPTION=.*/SMTP_ENCRYPTION=none/' .env && docker compose up -d authelia
   ```
   The log shows `SMTP_ENCRYPTION must be starttls, ssltls or none (is: 'tls')`,
   and the container is restarting. Setting `none` back (what `run.sh` uses)
   brings it up again.
