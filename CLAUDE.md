## Decisions (with the reasons)
- **Base:** OpenCloud's production line, 7.2.x. Rolling releases come every ~3 weeks, often a new major, and are not for customer servers. Don't rebuild for every patch release: rebuild for security fixes or bugs that affect the user, otherwise bundle them.
- **One image:** the official image with only `/usr/bin/opencloud` replaced, and the patched web embedded in the binary (option A). One immutable tag per server means no web/server drift. The rejected option B (web from a mounted folder) risked an old web folder silently winning over a new built-in one.
- **Branding at runtime, not in the build:** OpenCloud merges `themes/_branding/theme.json` over its theme, and the user mounts a folder per server, read-only. In 7.2 the web UI has no branding editor; the folder is edited on the host, by a separate management tool (planned outside this repo). This repo owns the folder's format: if a change adds or renames `theme.json` keys, update the README "Branding".
- **Move action patched too:** the web's `canBeMoved` required delete permission. Drag and drop and Ctrl+X/V never checked it.
- **The sign-in page patch (IDP)** came later, at the user's request. It's opt-in through `common.signin.*` and looks like upstream without branding.
- **Public repo and public image:** covers the AGPL source offer for the web, and servers pull without tokens.
- **Licences:** server and reva Apache-2.0, web AGPL-3.0, the repo AGPL-3.0. "OpenCloud" is OpenCloud GmbH's trademark, so customers should see the user's branding, not "OpenCloud" passed off as theirs.
- **Commits are GPG-signed:** key `F6FEA88C37C6A221` (ed25519, no passphrase, on this VM and on GitHub, expires 2028-10-20); the repo config sets `commit.gpgsign` and `tag.gpgsign`. The author is `kovacsakos <kovacsakos12@gmail.com>`.
- **Optional sign-in with 2FA: Authelia, a tested companion, not part of the image** (decided 2026-10-22; README "Status"). OpenCloud's built-in IdP has no 2FA. Authelia runs in its own container in the same compose stack under `/authelia` on OpenCloud's own name; OpenCloud with `OC_EXCLUDE_RUN_SERVICES=idp`, `PROXY_AUTOPROVISION_ACCOUNTS=false`, `PROXY_ROLE_ASSIGNMENT_DRIVER=default` (the `oidc` driver breaks the desktop client: opencloud-compose#111, desktop#217); users stay in OpenCloud's IDM, Authelia's file backend holds passwords, groups and TOTP devices; 2FA only for an admins group. Not in the image because of Authelia's own release cycle, data and process (no supervisor in this image). Instead: `versions.env` pins the tested Authelia version, the repo holds the reference setup and the tests cover the pair. **Without Authelia nothing changes:** the built-in IdP and upstream's password dialog. Patch 6 (`web/0004`, released in 7.2.4-4; from 7.2.4-6 the patch is `0004-account-pages-password-link-and-notifications`) makes "Change password" open a URL from the web config, and is a no-op without it: it reuses upstream's `accountEditLink.href` (`WEB_OPTION_ACCOUNT_EDIT_LINK_HREF`), because the server passes only the web options its Go struct knows (a new option would need a server patch too), and it removes the "Edit" button that option shows on Settings → Profile (the user's choice: Authelia is reached only through "Change password"). The row also shows when `change_password_self_disabled` is set, as long as the link is.
- **`deploy/` (2026-10-22), the user's choices:** SWAG in front (Let's Encrypt), reaching the containers by name over a shared Docker network (`SWAG_NETWORK`; container names `<OC_STACK>-opencloud`/`-authelia`, so several stacks fit on one host); one set of `SMTP_*` for Authelia and OpenCloud's `notifications` (both switched on by `SMTP_HOST` in the containers' entrypoints, so `.env` stays the only settings file); `users.sh` in this public repo. Tools on the host: Docker only (yq and Authelia's CLI run as containers; OpenCloud's API through `curl` inside its container, the token and body via curl's config on stdin).
- **User types and our share role (7.2.4-6, the user's choices on 2026-10-26):** oc-custom's file-server changes apply to two user types of our own, **Client** and **Employee**, and the share role **"Can't delete"** (Can upload + `GetQuota`, folders only); upstream's types and roles behave as upstream's. Everything is built into the image: a slim compose file must get every feature, so the types are added to upstream's default settings bundles in code (`server/0002`, not `SETTINGS_BUNDLES_PATH`: a file would freeze upstream's defaults and need regenerating at each update), the role is a built-in role (`server/0003`, enabled by default without `GRAPH_AVAILABLE_ROLES`, which would freeze the role list), and `FRONTEND_DISABLE_RADICALE`/`FRONTEND_CONFIGURABLE_NOTIFICATIONS` are `ENV` in the Dockerfile. Client: `Language.ReadWrite` only. Employee: language and the e-mail notification settings (no `Shares.Write`: no resharing, see Findings; no auto-accept). Neither has a personal space, favourites or public links. Admins stay upstream's Admin with upstream's web UI (they share client folders from Personal). Upstream's "Can upload" stays upstream's (the server allows move, the apps don't offer it). The web asks one table (`web/0011`, `ocCustomFeatures`) which change applies to which type; changes that follow a share's permissions (`web/0001`, `web/0012`) or are global (`web/0002`, `0004`, `0005`, `0010`, `server/0001`) don't. Ids: Client `38f0649f-b600-4188-b138-fbd2c773cc43`, Employee `12047bc6-9aa3-49f6-8d78-e64b3065cd99`, "Can't delete" `a61a37ad-42f2-46f6-a047-fe1906b525e2` (also in `deploy/users.sh`, `test/type-users`, `scripts/smoke-test`). Set aside: the type table in `theme.json`. (The server-side "no overwrite" rule for "Can't delete" is `reva/0003`, decided 2026-10-26: an upload over a file with content is refused, an empty file may be replaced for Windows Explorer and macOS Finder; upstream's roles keep overwriting.)
- **A plain file server (7.2.4-5, the user's choices on 2026-10-22; from 7.2.4-6 for Clients and Employees only, see above, so "everyone" below now means those two types):** everyone lands on "Shared with me" and Shares is the first menu entry; Spaces, Calendar and the Text Editor's menu entries are hidden (Text Editor still opens files); no hiding of shares; no "Copy permanent link" for User Light; the share dialog finds usernames. Hidden, not removed, where upstream allows it (Calendar is a setting, `FRONTEND_DISABLE_RADICALE`). The user asked for Nextcloud's one-tree layout (shares inside the personal folder); not possible: shares are their own space, and the desktop client refuses nested sync folders (`folderman.cpp`). For clients (Clients, only the Shares space) "Configure manually" with the Shares space synced straight into `C:\Users\<x>\OpenCloud` comes closest; staff get `OpenCloud\Personal` + `OpenCloud\Shares` with "Sync everything".
- **Log out with Authelia (patch 12, `web/0010`, 7.2.4-5):** Authelia 4.39.28 publishes no `end_session_endpoint` (no RP-initiated logout; the binary has no route for it), so the web's `logoutUser` only dropped its own tokens. Patch 12 sends "Log out" to `WEB_OPTION_LOGOUT_URL` in that case (upstream's option; the server drops unknown web options), and patch 6 hides the "Show devices" row that option adds on the profile page. `deploy/` sets it to `https://<domain>/authelia/logout?rd=<https://<domain>/, encoded>`.
- **Builds run in GitHub Actions only:** this VM (2 vCPU, 3 GB RAM, ~1 GB free) can't link the server. Small parts can be built locally: the IDP frontend took 2 min, the web's `pnpm install` 75 s.

## Findings (things that cost time)
- **SWAG's `proxy.conf` has `proxy_redirect http:// $scheme://;`**: it turned Authelia's final redirect to the desktop app (`http://127.0.0.1:<port>`) into `https://`, so the app's sign-in failed. `proxy_redirect off` next to it is a "duplicate" error; nginx uses the first matching `proxy_redirect`, so the site puts pass-through rules for `http://127.0.0.1` and `http://localhost` before the include. Only the real SWAG image showed it (the spike used Caddy).
- **SWAG without Let's Encrypt (tests):** put a certificate in `config/etc/letsencrypt/live/<first subdomain>.<URL>/{fullchain,privkey}.pem` before the first start; `init-certbot-config` then says "Certificate exists; parameters unchanged" (`keys/letsencrypt` is a symlink there, recreated at start).
- **Authelia:** a notifier SMTP check at startup is fatal when the mail server can't be reached (`AUTHELIA_NOTIFIER_DISABLE_STARTUP_CHECK=true` in `deploy/`); an SMTP password env var together with the filesystem notifier is "only one notifier" (so the entrypoint sets one or the other); its template `squote`/`msquote` don't escape quotes and there's no `toJson`; `authelia storage user totp delete` fails with "no TOTP configuration" when there's none; session elevation (e-mailed codes) is rate-limited per client (test override disables it); a TOTP code from the same 30 s window as the user's last one is refused (registering right after signing in); it rewrites the user file itself when a user changes their password. Behind SWAG it logs the client's address, not SWAG's.
- **OpenCloud:** `opencloud list` (in the container) lists the running services; `POST /users/{id}/appRoleAssignments` with an empty `appRoleId` is accepted and leaves the user without a role; `GET /graph/v1.0/users/<username>` works (no id needed); the official image has `curl`, not `jq`.
- **The web's start page** (`/`) is the first visible nav item of the default app in registration order (`announceDefaults` in `web-runtime/src/container/bootstrap.ts`); the menu itself sorts by `priority`. Patch 8 (`web/0006`) sorts the files app's list by priority, so one priority change moves Shares to the top and makes it the start page.
- **The share dialog's search:** the server's Graph search matches `uid`, mail and displayName and returns `onPremisesSamAccountName` to normal users; `filterRecipients` in `InviteCollaboratorForm.vue` re-filtered on display name and mail only.
- **Built-in web apps get no app config** (only `external_apps` do, or a whole `WEB_UI_CONFIG_FILE`, which replaces all `WEB_OPTION_*`), so the Text Editor's `primaryExtensions` default is patched.
- **Resharing:** no share role (reva `conversions/role.go`) carries `AddGrant`; User Light and Client have neither `Shares.Write` nor `PublicLink.Write`, and reva checks both. Internal links and "Copy permanent link" are only addresses.
  Resharing a folder that was shared to you isn't possible in 7.2.4, whatever the user's permissions: reva's `usershareprovider.go` (CreateShare) needs `AddGrant` on the item ("no permission to add grants on shared resource") and refuses folder shares that carry grant permissions ("resharing not supported", even for the admin). It would take a reva patch plus a share role of our own, and it behaves unlike Nextcloud: one level only, and removing a user's share doesn't remove the shares they made. The user decided against it on 2026-10-26 (not needed for now).
- **`upstream/server` can go stale:** on 2026-10-22 it still had patch 5 from before 7.2.4-3, and `scripts/refresh-patches` wrote that old version back. Check `git -C upstream/<part> apply --reverse --check ../../patches/...` for every patch before refreshing (all matched afterwards).
- **test/browser:** the test env's migrated users (alice) use German; select by links and IDs, not labels. `test/deploy`'s second browser has the default 800×600 viewport, where the left menu is collapsed.
- **Puppeteer:** leaving OpenCloud's page with `goto` never settles (open a new tab); a request-interception of the loopback redirect didn't fire through SWAG, so `desktop.js` listens on the port like the app does.
- **The server repo vendors its dependencies:** a `go.mod` replace of reva fails `go-generate` with "inconsistent vendoring". So `scripts/build-native` applies `patches/reva` to `vendor/github.com/opencloud-eu/reva/v2` (identical to the pinned reva tag, without tests). The `upstream/reva` clone is only for reva's unit tests and for `scripts/compat`.
- **The official binary isn't static:** it's built with `release-linux-docker-amd64` and links Alpine's libvips. `golang-ci:1.25` and the 7.2.4 image are both Alpine 3.24.1 with vips 8.18.2, so the binary drops in; `build-native` checks `ldd`. Re-check this when the base changes.
- **The version string:** `VERSION=v7.2.4 STRING=custom.<BUILD> EDITION=stable` gives `7.2.4+custom.1` in `opencloud version`, in `status.php` and in the web UI's footer.
- **Upstream's toolchain:**
  - The IDP needs `quay.io/opencloudeu/nodejs-ci:24` (pnpm 10), with the **whole server repo mounted**, because its Makefile includes `../../.make`.
  - The web pins pnpm 11.5.2, so it builds in `node:24-alpine` with corepack.
- **Running the web's tests outside `build-native`:** in `node:24-alpine` with corepack, set `CI=true` or pnpm's deps check aborts ("Aborted removal of modules directory due to no TTY") and `pnpm install --frozen-lockfile` first (~1 min). Template comments show up in vitest snapshots (Vue keeps them in dev), so put `oc-custom:` markers in the `<script>` part. The mocked capabilities default to `change_password_self_disabled` being true.
- **Vitest 4's `-u`/`--update` takes an optional value:** `pnpm test:unit --run -u <file>` swallows the file and runs the whole suite (an hour on this VM). Put the flag last: `pnpm test:unit --run <file> -u`.
- **The table patch doesn't update upstream's snapshots,** which record the default view (AppBar, Projects, trash Overview, admin Users and Spaces), because they'd conflict on every release. Those snapshot tests expect tiles. The build doesn't run them.
- **Patch robustness:**
  - The reva test lives in its own file (`role_custom_test.go`): appending to `role_test.go` conflicted with 8.x.
  - No two patches may touch the same file (`scripts/refresh-patches` rewrites each patch from the files it already touches).
- **`curl … | grep -q` under `set -o pipefail` fails on large responses:** grep exits early and curl's broken pipe fails the pipeline. Read responses into a variable first (`scripts/smoke-test`).
- **Puppeteer inside the OpenCloud web app:** `page.goto` never settles, because the app keeps a notifications connection open. Navigate in-app (click links), as `test/browser.js` does. The context menu is `#oc-files-context-menu`; actions have `oc-files-actions-<name>-trigger` classes.
- **`IDP_ASSET_PATH`** serves the IDP from disk, layered over the built-in copy. With it, the patched sign-in page can be tested on the official image without a server build. That's how patch 5 was checked.
- **reva's unit tests need its Go version:** run them in `golang:1.25-alpine` (reva's `go.mod`) with `GOTOOLCHAIN=local`; in 1.27 a dependency fails to build (`http2.TrailerPrefix`). The server's tests run in 1.27 with `GOFLAGS=-mod=vendor`.
- **"Can't delete" in the old OCS share API:** reva names a share by its permission bits, and our set (Can upload plus `GetQuota`) still comes out as `editor-lite` there (its "read" bit also needs `ListRecycle`). Graph, the web and the apps go by Graph's role id. Graph's legacy role names are only used for spaces.
- **reva has two copies of decomposedfs:** `pkg/storage/pkg/decomposedfs` (used by the `posix` driver, OpenCloud 7.2's default) and `pkg/storage/utils/decomposedfs` (`ocis`, `s3ng`). A storage patch must change both, with tests in both; a unit test of only the `utils` copy proves nothing for a default server (`reva/0002` and `reva/0003` were first written that way and did nothing on 7.2). The storage log's `line` field shows which copy runs. In the `pkg` copy's test env, `AssemblePermissions` keeps answering with the owner's permissions after setup, so a test that mocks other permissions has to clear `ExpectedCalls` first.
- **A new server needs `opencloud init` once:** without `/etc/opencloud/opencloud.yaml`, `opencloud server` exits at once ("The jwt_secret has not been set properly…"), so the container stops (and restarts in a loop) and there's nothing to `exec` into. The image's entrypoint is `/usr/bin/opencloud` with command `server`; either a compose `entrypoint` runs `init` when the file is missing (`deploy/`), or `docker compose run --rm opencloud init --insecure false --admin-password …` once, after which the compose file needs no entrypoint (`OC_ADMIN_PASSWORD` is only read by `init`).
- **What `users.sh` spends its time on** (2 vCPU VM, 2026-10-27): a new container per call ~2 s (yq, Authelia's hash), `docker exec`/`docker compose exec` 0.2–0.6 s, the admin token through OpenCloud's CLI ~3 s. Hence one yq container per run (`yq_start`), the hash in the running Authelia, and the token only after a command's checks; an `add` went from 13–24 s to 8–14 s. `EXIT_HOOKS` run last-added first.
- **Admin settings → Users lists roles from Graph's applications** (`listApplications`, the same list as `GET /graph/v1.0/applications`), so our user types show there with no web change.
- **Backing up OpenCloud's data folder:** the storage keeps file names and ids in extended attributes. A plain `tar` loses them, and a restored storage fails with "user.oc.name: no data available". Use `tar --xattrs --xattrs-include='*'`, or rebuild the test environment instead.
- **User types stay in the settings store:** every bundle OpenCloud has written (at each start, from its defaults or `SETTINGS_BUNDLES_PATH`) is kept and listed, even after it's gone from the defaults; upstream's are rewritten at each start. Removing one of ours means deleting it from the store.
- **Don't write to the test environment's test data as a test user;** checks that change files belong to its own tests. See `CLAUDE.local.md`.
